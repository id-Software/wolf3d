## Architecture readiness assessment

### Findings

| Area | Assessment | Evidence and consequence |
| --- | --- | --- |
| Engine/platform separation | **Ready baseline** | SDL includes are confined to `main.c` and `src/platform/`; engine harnesses compile with only the file adapters. Logical controls, audio and simulation are testable without devices. |
| Engine/game/content separation | **Prerequisite required** | `WL_DEF.h`, global runtime arrays, hard-coded resource numbers and WL6 names still combine engine mechanics with one game's definitions. R1 must classify identity/content; R2 must add content/world owners rather than extending these globals. |
| Asset ownership/lifetimes | **Usable but legacy-bound** | `ID_CA` owns graphics chunks, `ID_PM` owns cached pages, `ID_MAP` owns the cached map, and SDL owns presentation objects. Shutdown is explicit and partial-init cleanup is tested. Borrowed raw pointers are invalid after cache shutdown, so future APIs must expose qualified views/handles rather than these pointers. |
| Map loading | **Safe legacy adapter, not authoring model** | `CA_ReadMap` stages and bounds every fixed 64x64 plane before `CA_InstallMap`; `SetupGameLevel` validates selection, spawn, enclosure, doors, textures and sprites before play. It supports only 60 WL6 slots and must remain an import/compatibility adapter. |
| Renderer/content independence | **PARTIAL** | Enhanced rendering can consume immutable presentation snapshots and caller-owned targets. Both renderers still obtain fixed 64x64 VSWAP pages, numeric shapes and global framebuffer/UI definitions; Classic also performs visibility/activation/bonus side effects. R2 needs one catalog/image-view boundary, not renderer-specific loaders. |
| Classic/Enhanced compatibility | **Ready baseline** | Exact 32-capture baselines cover Classic corrected 4:3 and Enhanced 4:3, 16:9, 16:10, 21:9, 32:9 and Auto plus doors, pushwalls, edge clipping, HUD and restoration. Physical backends remain untested. |
| Native C boundaries | **Suitable seam, incomplete future API** | Existing loader, simulation, snapshot, render-target and file-adapter functions are C11. No authored-world, package catalog, manifest or transaction API exists yet; R2/R4 must provide SDL-free ownership and errors before Workshop/UI use. |
| Headless testing | **Ready baseline** | Synthetic archive generation and C harnesses cover deterministic fixed-step behavior, malformed data, lifecycle, both render paths and failure injection without proprietary inputs. State isolation still depends on ordered global reset. |

The current engine is therefore suitable for careful incremental R1/R2 work,
but it is not yet a general first-person creation engine. The recommended path
is to preserve the legacy adapter and both renderers while inserting small,
owned and testable content/world boundaries. A broad engine context, ECS,
renderer rewrite or Workshop-driven mutation of runtime globals is not justified.

## Future content-system requirements

These are requirements for future approved revisions, not implemented behavior
or ABI promises.

### Package and development model

1. Define one versioned package manifest before adding archive support. A
   complete game package names its game identity, manifest/schema versions,
   engine compatibility, campaigns and every required resource. Launch must
   not silently fall back to legacy Wolfenstein data.
2. Resolve the same validated logical path namespace from either a loose
   development directory or a PK3-compatible ZIP container. Directory and ZIP
   inputs must produce the same catalog identity and diagnostics.
3. Treat PK3 as a packaging convention only. Reading ZIP files does **not**
   imply ECWolf/GZDoom namespace, script, actor, map or mod compatibility.
   Compatibility claims require separately specified adapters and fixtures.
4. Keep the first model simple: one selected complete base game package, with
   optional explicitly ordered add-on packages only after deterministic
   override and dependency rules are approved. Do not begin with GZDoom-style
   implicit namespace behavior or a general scripting system.

### Data and resource model

- Use stable string or numeric content IDs resolved through an owned catalog,
  never raw VSWAP page numbers outside the legacy adapter.
- Represent maps, textures, sprites/animation, audio, fonts/UI and metadata
  with bounded descriptors carrying dimensions, formats, ownership, opacity,
  pivots/scales and required/optional status.
- Define weapons, enemies, items and gameplay parameters as validated data while
  native C owns deterministic behavior implementations. Unknown behavior IDs
  fail clearly; data must not become unbounded executable scripting.
- Define campaigns as ordered map/objective/progression graphs with validated
  starts, exits, unlocks and completion rules. Keep durable authored definitions
  separate from transient actors, visibility, doors, pushwalls and save state.
- Build both Classic and Enhanced render inputs from the same catalog/resource
  views. Preserve exact legacy 64x64 sampling through an adapter while adding
  dimension-safe descriptors and explicit fixed-point rounding rules.

### Selection, Workshop and export

- The main menu enumerates validated complete game/mod packs and displays
  identity, version, compatibility and validation errors before launch.
- Workshop uses the same authored-world and content IDs as gameplay. Its
  create/edit/save/playtest/export operations call SDL-free native C APIs; UI
  callbacks never own or directly mutate canonical world state.
- Playtest builds an isolated runtime session from a validated authored-world
  snapshot. Returning to Workshop must not persist transient gameplay state.
- Export writes a deterministic loose directory or PK3-compatible ZIP from the
  same validated catalog and manifest, using atomic output/recovery rules. Save,
  playtest and export belong to later milestones after the R2 contract.

### Validation and security

- Reject absolute paths, `..` traversal, drive prefixes, ambiguous/case-colliding
  names, duplicate entries, unsupported encryption/compression and symlink
  escapes. Normalize names before catalog insertion.
- Apply explicit limits to archive bytes, entry count, individual and expanded
  sizes, compression ratio, map/object/resource counts, image dimensions,
  animation frames, audio duration and total memory. Check integer arithmetic
  before allocation and decompression.
- Stage parsing and validation before publishing a catalog/world. On any error,
  destroy partial state and return bounded machine-readable diagnostics with
  package, path, resource ID and cause.
- Version manifests and formats independently. Unknown required fields or
  incompatible major versions fail; migrations are explicit, deterministic and
  fixture-tested. Checksums establish integrity, not authorship or licensing.
- Keep provenance and distribution rights in the package inventory. Security
  validation does not confer permission to redistribute content.

### Minimum native C ownership boundary

R2 should specify opaque owners and caller-visible views for a package source,
validated manifest/catalog, resource image/audio data and authored world. Core
operations need bounded readers, enumeration/lookup, validation, error access,
legacy import, session construction and destruction. File/ZIP adapters and SDL
menu/Workshop presentation remain outside the core. Returned data is either
owned by the caller or borrowed for a documented owner lifetime; no hidden
global cache pointer crosses the boundary.

## R1/R2 prerequisites and sequencing

1. R1 completes the file-level licence/provenance and identity/reference audit,
   defines legacy-content isolation and an original-only launch/package gate.
2. R2.1 freezes manifest, path, map, ID, version and limit contracts plus
   malformed/migration fixtures before a ZIP decoder is selected.
3. R2.2 adds staged SDL-free parsing and diagnostics; R2.3 adds the shared
   catalog/resource descriptors and legacy adapter.
4. R2.4 implements identical loose-directory and PK3-compatible resolution with
   traversal, collision, size and decompression protections.
5. R2.5/R2.6 prove legacy parity, valid/malformed/old package handling,
   deterministic catalog identity, bounded cleanup and both-renderer integration.
6. Main-menu selection, data-driven game breadth, Workshop, save/playtest and
   export remain later approved slices; do not pull them into the first loader.
