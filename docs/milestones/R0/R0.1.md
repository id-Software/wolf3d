# R0.1: source, asset and build inventory

Status: **PASS (Linux clean builds and regressions verified; Windows cross-build and Wine check verified)**. Audited 22 November 2026 on branch `docs/revival-roadmap-and-validation` from source commit `47db2a3`.

This report closes revision R0.1 only. R0 remains open: R0.2-R0.7 and acceptance criteria A05-A22 have not been performed.

## 1. Objective, scope and evidence rules

R0.1 establishes a reproducible baseline of the active C11/SDL3 port, its historical source and local research inputs, its CART build, current test surface, and the impact of higher-resolution replacement textures. It does not change rendering, simulation, maps, formats, assets or engine architecture.

Findings labelled **verified** were established by inspecting the named source or running the commands in section 9. **Recommendation** identifies future work, principally for R2; it is not implemented behavior. Licence/provenance entries describe repository evidence and are not legal clearance.

Inventory totals at the audited commit:

- 314 tracked files; 50 active `src/**/*.c` files and 40 active headers/includes.
- 16 Python test entry points and 35 C test harnesses.
- 108 tracked historical files under `WOLFSRC/`.
- Six tracked files under `third_party/` for emu8950.
- One ignored local research directory, `3rdparty/ECWolf_RMST/`; it is not part of the repository.

## 3. Rendering, timing and gameplay pipeline

### Raycasting and rendering

The Classic path is `GameStep` -> `ThreeDRefresh` -> one `CastRay`/`AsmRefresh` per viewport column -> `ScalePost` for grouped wall columns -> `DrawScaleds`/`ScaleShape` for statics and actors -> weapon overlay -> SDL palette expansion/presentation. `CastRay` traverses the fixed 64x64 grid, handles ordinary walls, doors and moving pushwalls separately, computes VSWAP page/column and rejects rays escaping the map.

The Enhanced path keeps the Classic framebuffer for UI/HUD composition but, during an active world view, `VL_DrawScreen` calls `WL_RenderSnapshot`. `Scene` resamples the same ray intersections at each target column, keeps a depth column, draws walls, then stable-sorts transparent sprites far-to-near. `WL_RenderSnapshot` centers the original 4:3 UI within the selected gameplay aspect. This path is presentation-only; snapshots copy the relevant world state so interpolation does not mutate simulation.

### Game loop, clock and determinism

`main` converts SDL nanoseconds to rational 70 Hz deadlines and advances at most eight ticks per outer-loop batch. `WL_PLAY.c::GameStep` uses one-tic normal updates, four-tic original demo commands, and clamps long non-demo elapsed batches to `MAXTICS` (10). Doors, pushwalls, player input, actors, audio location, palette, render and snapshot capture are ordered explicitly within each authoritative tic. Smooth rendering samples `WL_PRESENT` snapshots at display cadence; it does not alter `gamestate.TimeCount` or RNG order.

### Movement, collision and gameplay

`TryMove` tests the player's `MINDIST` square against map tiles/solid doors, blocking statics and nearby shootable actors. `ClipMove` attempts the combined move then slides on one axis in the preserved order. Classic and Modern controls share these collision primitives; Modern combines normalized forward/strafe translation once per tic. Doors and pushwalls use the same `tilemap` and actor reservations. Actor behavior remains table/state-driven through `WL_STATE.c`/`WL_ACT2.c`; bounded pools are checked for allocation failure.

Hardcoded model constraints verified in source include 64x64 maps, 64 doors, fixed tile size `TILEGLOBAL=65536`, 304-column maximum Classic viewport, at most 49 collected Classic sprites (in a 50-entry local array), bounded actor/static pools, six episodes of ten map slots, fixed WL6 resource names and a 70 Hz authoritative clock. These are compatibility constraints until a later revision explicitly changes and tests them.

## 4. Data, maps, saves and resource ownership

### Input formats

- `CA_Startup` requires external `VSWAP.WL6`, `GAMEMAPS.WL6`, `MAPHEAD.WL6`, `AUDIOT.WL6`, and `AUDIOHED.WL6`, then opens `VGADICT.WL6`, `VGAHEAD.WL6`, and `VGAGRAPH.WL6`. Input is read in place and capped at 32 MiB per file; graphics expansion is capped at 4 MiB.
- `ID_MAP.h::maptype` contains three 64x64 word planes plus a name/number. `CA_ReadMap` accepts only 60 WL6 map indices and map headers whose width and height are both 64. It bounds and decompresses every plane before installing it.
- `SetupGameLevel` derives the runtime x-major `tilemap[64][64]`, door list, actors/statics and area connectivity. It validates the single player start, reachable perimeter enclosure, referenced wall pages and sprite streams before play.
- VSWAP ownership is `PM_Startup`/`PM_Shutdown`; pages are cached lazily and freed on shutdown. Map ownership is `CA_CacheMap`/`CA_UncacheMap`. Graphics chunks are owned by `ID_CA`; high-resolution render surfaces and SDL textures are owned by `sdl_video.c`.

### Save and configuration formats

Native saves are six `slotN.w3s` files, not DOS-compatible saves. Version 1 begins with `W3RSAVE`, a 96-byte little-endian header, bounded payload (maximum 256 KiB), CRC, slot/episode/level/difficulty metadata and CRC identities for MAPHEAD/GAMEMAPS/VSWAP. Actor pointers and state pointers are serialized as validated indices/IDs, never native addresses. `Save_Load` stages and validates all state/resources before its final map install and state application. `SaveFile_WriteAtomic` uses exclusive temporary files, flush/fsync and atomic replacement/create rules.

Configuration is a bounded TOML subset stored beside saves in the SDL preference directory. It includes controls, audio, Classic view size and display preferences; it is independent of map content and native save version.

No editable Workshop map or content-package format exists. The current map representation is fixed legacy WL6 input plus transient native arrays; R2 must define the shared versioned content contract before R4 authoring APIs.

## 5. Build configuration, dependencies and platforms

`cart.toml` selects C11, GCC, the `sdl-renderer` backend, libm and strict warning flags on Linux/Windows. The default SDL root is ignored `vendor/SDL` with shared linkage. Profile `cart-sdl` reuses `../cart/vendor/SDL` statically and adds pthread; it performs no download. The active source also compiles the bundled emu8950 C sources through `ID_OPL*.c`.

Verified local dependencies:

- Linux x86_64, GCC 14.2.0, Python 3.13.5, CART 0.2.0.
- sibling SDL checkout with static `libSDL3.a`; project documentation records that checkout as SDL development 3.5.0 revision `08b9c5539`.
- MinGW GCC and an ignored SDL 3.4.18 x86_64 MinGW SDK for cross-compilation; Wine 10.0 for a compatibility smoke.

CART has no native desktop debug/release selector. Its configured build command emitted both its built-in `-O0 -g` and project `-O2`; GCC applies the last optimization option, producing optimized objects with debug information. R0.1 therefore treats that clean CART build as release-like and uses the documented explicit source/link list with `-O0 -g3 -Werror` for the clean debug build. `cart doctor` cannot accept `--profile`; base doctor correctly fails because ignored `vendor/SDL` is absent.

Windows source compatibility is supported by `_WIN32` file/path branches and the Windows section in `cart.toml`. R0.1 cross-linked all current sources with strict warnings and passed `--check-level` under Wine. This is not native physical-Windows video, audio, input, DPI or filesystem verification.

## 7. Texture and sprite compatibility assessment

### Local reference inventory and provenance

The ignored `3rdparty/ECWolf_RMST/ECWolf_RMST.pk3` was enumerated read-only. It contains 1,032 PNGs:

| Dimensions | Count |
| --- | ---: |
| 128x128 | 1,011 |
| 16x32 | 13 |
| 96x48 | 4 |
| 640x80, 1776x26, 1506x20, 104x88 | one each |

The companion SFX archive contains 106 audio entries. The supplied readme credits many contributors and includes id Software and other game studios, but states no redistribution licence. **Provenance status: local research input, rights unverified, not distributable by this project.** The entire `/3rdparty/` directory is ignored and remained untracked.

### Current support: fixed 64x64, not arbitrary dimensions

The engine cannot directly load PNGs and does not support arbitrary wall/sprite dimensions. It consumes 8-bit indexed VSWAP resources:

- `ID_PM.c::PM_Startup` requires every pre-sprite wall page to be exactly 4,096 bytes.
- `WL_DRAW.c::CastRay` derives wall texture columns with `>>10` and `&63`, returning 0-63; `ThreeDRefresh` reads `page + column*64` and requires a 4,096-byte page.
- `WL_SCALE.c::ScalePost` iterates exactly 64 wall rows and divides vertical scaling by 64.
- `PM_DecodeSprite` validates original post bounds against 64 columns/rows and decodes into fixed `pixels[4096]` and `opaque[4096]` arrays.
- Classic `DrawShape` and Enhanced `WL_RENDER.c::Shape` loop 64 source columns/rows and index `sy*64+sx`.
- Enhanced `Scene` requires 4,096-byte wall pages, converts wall height with a `64.0/height` scale, clamps rows at 63, and indexes `column*64+row`.

### Separate compatibility findings

**Wall textures.** Ray/world intersection and projected wall height are independent of bitmap resolution, but `rayhit.column`, VSWAP validation, page layout and both samplers are fixed to 64. A 128x128 wall cannot be substituted without changing the resource descriptor and normalized-u sampling. Merely accepting a 16,384-byte page would still select only 64 columns/rows incorrectly.

**World-space sprites.** Projected sprite width is derived from world distance (`65536*focal/nx`) rather than source pixel count, which is the right basis for preserving a one-tile visual size. However, pixel iteration, original two-half anchoring around source columns 31/32, sprite header validation and temporary buffers are 64-specific. A 128x128 replacement should preserve the same world-space width by default and use explicit pivot/extent metadata where an asset intentionally differs; doubling pixel dimensions must not double the actor's physical or visual world size accidentally.

**Transparency.** Original sprites use post commands plus a separate boolean opacity plane, so palette index zero may be opaque. PNG alpha cannot be treated as a zero-colour key. A future loader must preserve explicit alpha/opacity, define indexed-palette conversion or a renderer format boundary, and test opaque zero, partial/absent alpha, malformed dimensions and bounded allocations.

**Texture coordinates and scaling.** Wall u/v and sprite source coordinates must be normalized or parameterized by `width`, `height` and `stride`. Classic needs deterministic integer sampling into a 320x200 target; Enhanced may sample the same decoded resource at native output resolution. Both must retain wall flips, door/pushwall offsets, sprite pivoting, occlusion against `wallheight`/depth and stable far-to-near transparency.

**Display modes.** Original/Classic and Enhanced select output resolution and aspect, not resource resolution. Higher-resolution source art should be a content/resource choice orthogonal to display mode. Classic may downsample it; Enhanced may expose more detail. The 4:3 UI/HUD remains centered even when the world aspect is 16:9 through 32:9. Tests must cover both renderers, all relevant aspects, view sizes, HUD/weapon overlays and screenshots; support in only Enhanced would not be general texture support.

### R2 recommendations

1. Keep legacy VSWAP decoding as a compatibility adapter. Introduce a bounded resource descriptor with role, width, height, stride/format, pixels, explicit opacity and pivot/scale metadata; do not infer role from dimensions.
2. Change ray hits to carry a normalized or fixed-point horizontal coordinate, then sample using the selected wall width. Parameterize vertical sampling. Preserve exact 64x64 behavior in legacy fixtures.
3. Replace fixed sprite decode buffers at the resource boundary with bounded owned images; parameterize both Classic and Enhanced sprite loops. Keep world size independent of source pixel resolution.
4. Define named resources and a manifest before adding PNG decoding. Validate maximum dimensions/bytes, integer overflow, alpha rules, missing resources and mixed packs. The 16x32/96x48/banner images are not automatically wall or world-sprite candidates.
5. Add original redistributable 64x64 and 128x128 fixtures that exercise wall flips, doors, pushwalls, transparent/opaque-zero sprites, pivots, weapons and both display modes. Do not derive fixtures from ECWolf_RMST.
6. Treat the remaster archive as measurements only until each asset's distribution rights and provenance are explicitly cleared.

## 12. Revision contract and review checklist

**Prerequisites.** The audited source commit and branch are named at the top of
this report. Build prerequisites and their verified versions are in sections 5
and 9. Private compatibility checks require a user-owned external WL6 data set;
the synthetic suite does not.

**In scope.** Read-only source/asset/format inspection, clean builds, existing
tests and smokes, texture-resolution compatibility analysis, this evidence
report and the playbook update. **Out of scope:** runtime refactoring, new
resource/map formats, asset conversion or redistribution, new automation
frameworks, sanitizers/visual baselines belonging to later R0 revisions, and
R2 implementation.

**Affected modules and C APIs.** No C module or API changed. Sections 2-7 list
the inspected owners and functions. The only tracked changes are documentation.

**Fixtures/assets.** No fixture or artwork was added. Existing tests generated
their synthetic fixtures in temporary directories. Owned WL6 and ECWolf_RMST
were read-only external inputs and remained ignored. Future 128x128 fixtures
must be original and redistributable.

**Validation/regression and failure injection.** Section 9 is the executable
validation contract for this revision. The full existing suite was the required
regression. Existing malformed-resource, injected display failure, atomic-write
failure, corrupt configuration/save and unavailable-device cases ran within
that suite; R0.1 added no new fault-injection mechanism.

**Measured limits.** Recorded code limits include 32 MiB input files, 4 MiB
expanded graphics chunks, 4,096 VSWAP pages maximum, 64x64 maps/textures,
256 KiB save payloads and 4096x2160 Enhanced render targets. Test wall time is
reported for reproducibility, not as a performance acceptance threshold.

**Review checklist.** Confirm that (1) no runtime or asset file changed,
(2) each A01-A04 state cites executed or inspected evidence, (3) external asset
rights remain unclaimed, (4) debug/release/CART qualifications are retained,
(5) omitted platforms and later R0 gates remain explicit, (6) commands in the
playbook exist now, and proposed commands remain labelled unimplemented, and
(7) no ignored third-party or generated artifact is staged.

**Rollback.** Revert the documentation commit. No engine behavior, format,
dependency or user data requires migration. Ignored `build/validation/R0.1/`
evidence can be discarded independently after review.
